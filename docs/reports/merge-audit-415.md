# Merge audit: #415, axiom wave two

*30 October 2026. For #485. The history was read with Git at main 32eebe4ba, and every file and line cited below was read again at main 05640d4c7; none of the files cited changed between the two. The audit changed no file but this one.*

The merge that landed #415, axiom wave two (b77b645f, 24 October 2026, 216 files), put back an older version of README's row for the formal model, and so lost #375's account of the model's replay. This audit asked whether main's text was lost anywhere else in the same way. That row is the only loss, and 5e33da16a (#489) has put it back. The line scan found 29 other places where a merge left out lines from main's side: in 24 the axiom retirement rewrote main's words on purpose, and in 5 the text was generated, stamped or moved, and main has replaced or moved it since. The other passes found more in the branch's merges of other branches, each intended or superseded in the same ways.

## Method

**The merge.** b77b645f has two parents: main at 69850d21b, and the branch's tip at 65db996e5. Two facts settle where to look:

- `git diff --quiet b77b645f 65db996e5` exits 0, so the merge's tree is the branch's tree, file for file.
- `git merge-base 69850d21b 65db996e5` gives 69850d21b, so all of main was already in the branch, and main's side brought nothing the branch had not merged.

So b77b645f resolved nothing by hand, and all 216 files it changed came from the branch as it stood.

Against its second parent b77b645f changes nothing. Against its first parent, 69850d21b, it changes 216 files. 69850d21b is also the second parent of 518e67597, the branch's last merge of main, and only 65db996e5's regeneration comes after that merge. So each line of main's that b77b645f lacks was taken out on the branch, by an ordinary commit or by a merge that resolved a conflict for the branch's side, and comparing the 216 files against both parents comes down to reading those commits and merges, which the passes below do. 103 of the 216 are the generated edition, 101 pages under book/ with facts.json and CERTIFICATE.md, which render.py writes whole from the sources, and which 65db996e5 regenerated after the last merge. A loss there would follow a loss in a source, so the passes read the other 113.

**Where a loss must be.** Between 19 and 24 October 2026 the branch took in 64 merges, which `git rev-list --merges 69850d21b..65db996e5` lists beside 70 ordinary commits. Thirteen of them merged main: twelve on the branch itself, from 261c28ae7 to 518e67597, and 890032fd6 on a sub-branch the branch then merged. The other 51 merged the retirement's sub-branches, some of which carried main. In b77b645f main is the first parent, and in each merge of main it is the second. If a merge of main resolved a conflict by taking the branch's side, it dropped main's text there. Every later merge then carried the drop without a conflict, because its merge base already held main's text and the branch had changed it. b77b645f brought the result to main. So the search reads all 64 merges, since a sub-branch can carry main's text too, in these passes:

1. **The line scan.** For each merge, and each file both parents had changed since their merge base, the scan lists the lines one side added that the merge's result lacks. It keeps those whose side lies on main's line of first parents. It leaves out the generated edition (book/, facts.json, CERTIFICATE.md, GRAPH.md). It found 30 file-merges, in 8 merges, all on main's side. Sixteen merges have more than one merge base; the scan used the one `git merge-base` gives, and the merge-tree pass covers the rest.
2. **Each entry read.** Each of the 30 was read as a word-by-word diff of the merge against main's side, with the commits on each side that touched the file, and followed to the file on main today.
3. **Where each line came from.** A lost line counts as main's when the merge base lacked it and the newest commit that both the merge's side and 69850d21b contain held it (`git merge-base` of the two), so that text a sub-branch wrote, and main took in through that sub-branch's pull request, counts as main's too. This pass ran over the losses of every merge, on either side, to find text of main's that came in through a sub-branch.
4. **Each merge redone.** `git merge-tree` redid each of the 64 merges. The pass listed each file whose recorded result differs from the automatic one, whichever side had changed it.
5. **Copies counted.** The line scan again, counting the copies of each line instead of asking only whether it is there.
6. **Text put back.** Lines that main's side had deleted, a merge kept, and #415 then brought back to main.
7. **Ordinary commits.** The 70 ordinary commits, searched for lines main once had and had since removed, which a commit adds back, and for lines main had added since the branch began, which a commit deletes.
8. **Deleted and moved files.** The files a merge deleted, and the files either side moved.

## What the scan cannot see
